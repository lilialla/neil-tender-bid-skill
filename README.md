# neil-tender-bid-skill

这是一份给 AI 助手用的本地说明，外加几个检查脚本，用来协助准备中文投标文件。当前版本 `0.1.10`。

采购人发出招标文件、采购文件、询价文件或磋商文件之后，里面通常散落着很多必须满足的条件：谁有资格、要交什么证明、怎样评分、什么格式、什么期限、合同里还要承诺什么。这些话不一定集中在一页。漏掉一条、用错人、把上一版报价留在新文件里，都可能使这次响应无效。

这个仓库约定助手怎么把这些条件读全、列成一张可以核对的表、再按章节写响应。人决定用哪份材料、是否作出承诺、是否盖章和递交。脚本只核对文件有没有被换掉、编号是否对得上、同一事实在各章是否一致。

它不是投标网站，也不会登录采购平台、盖章或替你提交。

## 举一个例子

一份文件要求：派一名负责人，提供近三年两项同类业绩，并承诺两小时内响应。这三句话可能分别出现在资格条件、评分表和合同里。

按这里的做法，助手先把三句话都列进同一张要求表，并记下每句话在哪一页。你确认这张表之后，写“人员”和“服务安排”时使用同一组已经确认的人名和时限。如果后来换成另一个人，脚本标出人员表、证明页和承诺函里引用了这个人的位置，而不是把整本重写一遍。需要盖章的页从同一份总稿里抽出，不能在抽出的文件上另改价格或承诺。

工具不能判断这个人的经历够不够，也不能判断评委是否给分。

## 两样东西各做什么

**Skill** 是放进助手技能目录的一份操作说明，入口是 [skills/neil-tender-bid-skill/SKILL.md](skills/neil-tender-bid-skill/SKILL.md)。助手接到这类任务时先读它，再按步骤工作。

**脚本** 是 `skills/neil-tender-bid-skill/scripts/tender.py`。它做能重复执行的核对：文件有没有被换掉、页码对不对、要求编号齐不齐、人员和期限是否一致、PDF 每一页来自哪里。它不阅读采购文件的含义，也不会从关键词自动生成要求。原文必须由助手逐段读完。

历史标书只能当格式参考。不能用上一份响应倒推这次采购文件的要求。

## 一次准备分三步

业务文件放在本仓库以外的单独目录。真实采购文件、响应稿、证照、报价和会议记录不要提交到 GitHub。

### 1. 把要求列清

放入本次有效的采购正文、附件和补遗。助手读完全文，写成一张要求表 `requirements.csv`。每一行是一条可以单独回应的要求，固定九列：

| 列 | 记什么 |
|---|---|
| 编号 | 这条要求的稳定编号，后面各章都引用它 |
| 原文位置 | 在哪个文件、哪一页、页内什么地方 |
| 原文 | 相关原文本身，不只写关键词 |
| 要做的事 | 实际要满足什么 |
| 性质和后果 | 属于资格、评分、格式、程序还是合同；不满足会怎样。不自行写成废标 |
| 怎样算满足 | 对象、期间、数量、金额、分值 |
| 要交什么 | 响应正文，或证照、合同关键页等证明 |
| 疑点 | 还没弄清的地方，或已经作出的处理 |
| 状态 | 待复核、已确认、待澄清、已被补遗取代 |

同时用 `sources.json` 记录读了哪些文件、每一段有没有处理。有的页是扫描件、暂时读不出文字，就保持未读，不能当成“这一页没有要求”。

你看过这张表并明确说按这一版继续，才叫冻结。没人确认时，它只是工作稿。

### 2. 按章节写响应

从已经冻结的要求里先做两个相关章节，例如人员和服务安排。每章只拿到自己需要的原文、已确认的事实和证明页，不把整本采购文件和全部历史标书塞给每一章。

正文里的人名、时限、报价写在 `chapters.json` 的共用事实里，避免这一章写两小时、那一章写四小时。未知的事实留空或标成待核，不编成已经确认。

改一个已经写明的事实时，先找出引用了它的章节和证明，再改那些位置。两章做完，只说明这两章可用，不说明整本已经完成。

Word 和演示文稿用你电脑上已有的文档工具制作。这个仓库不生成 DOCX 或 PPT。

### 3. 核对整套文件

正文和证明都核对过之后，脚本才能合并已经生成的 PDF，并记录输出的每一页来自哪份文件的哪一页。需要盖章的页和其余页都从同一份总稿抽出。总稿改过之后，要重新抽页，不能在派生文件里另改业务内容。

文件状态分开记：还在编写、等待盖章、人已经批准递交、已经递交。有递交记录也不等于采购人已经接受。

## 安装

需要 Python 3.10 或更高版本。阅读来源、填写要求表和检查章节只用 Python 标准库。合并或拆分 PDF 时还需要 `pypdf==6.12.2`，版本写在 [requirements.txt](requirements.txt)。

把文件夹 `skills/neil-tender-bid-skill` 复制到助手读取技能的目录。Codex 的位置是：

```text
~/.codex/skills/neil-tender-bid-skill
```

那个位置已经有同名文件夹时，先比较两边差异，不要直接覆盖。

在本仓库里确认脚本能运行：

```bash
uv run --no-project --with-requirements requirements.txt \
  python skills/neil-tender-bid-skill/scripts/tender.py --help
```

没有 `uv` 时，用已经装好 `pypdf` 的 Python 运行同一条 `tender.py`。不确定某个子命令的参数时，运行 `tender.py <子命令> --help`，不要按名字猜测。

## 从一份采购文件开始

路径换成你自己的目录和文件。`init` 发现目标目录已经是一个项目时会拒绝覆盖。它只登记“有哪些文件待读”，并建立一张空的要求表，不会把要求提取出来。

```bash
python3 skills/neil-tender-bid-skill/scripts/tender.py init \
  --project "<新的项目目录>" \
  --source "<采购文件.pdf>"

python3 skills/neil-tender-bid-skill/scripts/tender.py check \
  --project "<项目目录>" \
  --full
```

然后让助手按照 Skill 逐段阅读，填写覆盖记录和要求表。表格、跨页内容和页脚注释都要读，不能只搜关键词。

采购文件如果是扫描件，先用识别工具把页面转成文字。本仓库不运行识别，也不会上传文件。已经用 MinerU 得到全本 `content_list` v1 结果时，可以把这份结果挂到原件上。它必须来自与原 PDF 字节完全相同的全本，不能是抽过页或重排过的文件。

```bash
python3 skills/neil-tender-bid-skill/scripts/tender.py attach-ocr \
  --project "<项目目录>" \
  --source "<已登记的采购原PDF>" \
  --input "<当时拿去识别的那份全本PDF>" \
  --result "<content_list.json>"
```

关联之后，每一页仍要对照原件核对。错一个字就在该页记下修正，不改原始识别结果。细则见 [扫描件的既有识别结果](skills/neil-tender-bid-skill/references/workflow.md#扫描pdf的既有ocr结果)。

## 命令

| 命令 | 什么时候用 |
|---|---|
| `init` | 新建项目目录，登记采购原件，建立空要求表 |
| `attach-ocr` | 扫描件已经有 MinerU 全本识别结果时，挂到原件上 |
| `check` | 看来源是否可读、要求表是否还能对回原文 |
| `freeze` | 你确认这一版要求之后，把确认记下来 |
| `replay` | 比较助手第一次列出的要求，和后来人工改过的表 |
| `packet` | 导出写某一章时允许看到的原文、事实和证明 |
| `render` | 只把模板里的 `{{人名}}` 这类标记换成已确认的值 |
| `chapters-check` | 看章节有没有回应要求、人和期限是否一致 |
| `impact` | 改了一个事实或一条要求后，找出要跟着改的章节 |
| `assemble` | 按指定页序合并 PDF，并记下每一页的来源 |
| `derive` | 从同一份总稿拆出待盖章页和其余页 |
| `status` | 查看当前这套文件处在编写、待盖章、待递交还是已递交 |

`chapters-check --chapter <章节ID>` 只检查正在写的章节。不带这个参数时，检查整张要求表有没有着落。局部没问题，不能当成整本完成。

## “通过”是什么意思

脚本把风险分成六类。每一类都要有人实际看过，不能把六个“通过”一次填完。

| 检查 | 人要确认的事 |
|---|---|
| G1 | 这次以哪几份文件为准，文件打得开，关键页读得出来 |
| G2 | 每条要求都能回到原文，跨页、脚注、勾选和附件没有丢 |
| G3 | 必须回应的内容和证明真的出现了，对象、时间和形式正确 |
| G4 | 主体、人员、期限、承诺和同一轮报价前后一致 |
| G5 | 目录、页码、表格、附件读得懂 |
| G6 | 现在要使用的就是这套文件，旧版本已经撤下 |

命令退出码 `0` 表示这次机械检查没有待核项或阻断项。`1` 表示查出了问题，问题会照实打印。`2` 表示命令本身没跑成，例如路径或参数不对。退出码不是允许递交。

文件名写成“定稿”、检查没有报错，或者手里有一张模拟回执，都不等于已经盖章、已经递交，或采购人已经接受。

## 测试

```bash
uv run --no-project --with-requirements requirements.txt python -m unittest discover -s tests
```

测试只用虚构文字和运行时生成的 PDF，不使用真实投标材料。`0.1.10` 记录的结果是 81 项通过。它们证明脚本能发现换了来源、人写错、期限写错、报价轮次冲突、PDF 抽错页这类问题。助手自由写出的段落仍要人读。这组测试不能证明一份新的采购文件已经被完整读懂。
