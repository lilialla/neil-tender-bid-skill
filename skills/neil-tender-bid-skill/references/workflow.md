# 操作与验收说明

按当前阶段读取：共同约定 → Phase 0 → Phase 1 → Phase 2。脚本只实现可重复检查；原文理解、证据证明力和实际页面复核由操作者承担。

## 共同约定

默认只维护三份主要数据：来源清单与覆盖合一 JSON、九列要求 CSV，以及 Phase 1 起逐步充实的分层章节 JSON。人工决定、变更、材料缺口和放行摘要写回现有清单，不另增审批表。

每个项目先识别已授权的来源、私有工作目录、现有状态及当前目标。新建业务目录或文件采用用户的 `YYMMDD+当日两位序号_名称_真实版本状态`，先查看目标目录当日序号；固定机器入口按脚本约定命名。真实数据不得写入 Skill 目录或源码仓库。

读取旧项目时，按现有清单的准确路径重新计算拟接续编辑稿及对应导出文件的哈希，与受检版本核对；不一致时先查明差异并确定本轮基线，不能把旧检查套到当前文件。原件、要求版本、适用检查规则或证件有效性判断时点变化，都会使受影响结论过期。沿用已回答且基础不变的业务决定，不重新发起形式确认。

运行 `python3 "<skill-root>/scripts/tender.py" --help` 查看唯一入口，子命令先读 `--help`。新建、冻结及派生操作使用当前实现的参数；不得将本文示意字段当作未验证接口。未具备的语义能力必须由 Codex 实际阅读完成。

Phase 0 当前命令如下。路径占位符需替换为本次已确认的实际目录；初始化拒绝覆盖既有工作目录：

```bash
python3 "<skill-root>/scripts/tender.py" init --project "<新项目内部工作目录>" --source "<采购原件>" --source "<必要附件>"
python3 "<skill-root>/scripts/tender.py" check --project "<项目内部工作目录>" --full
python3 "<skill-root>/scripts/tender.py" replay --candidate "<首次候选CSV>" --reviewed "<复核CSV>"
```

`init` 创建 `sources.json` 和 `requirements.csv`；只建立待核来源，不自动提取采购要求。`check` 返回 G1/G2、具体问题、风险提示、当前 `digest`、`can_freeze` 和 `freeze_status`。`risk_hints` 仅是回读辅助；`replay` 按稳定要求编号比较，无法自动裁定两条语义是否等价或高风险漏项是否为零。

### 授权自主回放与反馈修复

用户已授权自主制作或测试时，将本次对象、完成范围及采用假设记入现有章节清单，连续完成范围内各单元。原文和已有材料能解决的解释由操作者直接核对；真实金额、人员或新增承诺无依据时保留待核，内部测试可使用明确假设或占位继续。无需每完成一章就请求许可，也不为内部测试反复请求真实冻结；原总账与真实批准状态不变。

用户要求独立裁判时，执行者负责新工作副本，裁判从不继承执行者推理的上下文读取采购依据、实际产物和必要定位，先独立判断再看执行者结论。裁判意见须指明要求编号、来源与响应位置、差异及影响；其通过只适用于实际审查范围，不充当人工批准或采购人认可。整本任务不能用局部通过提前收口，也不能用要求编号齐全代替逐项实质核对。按已核实响应、证据待核、待执行、解释待核或有依据的不适用汇总实际处置；局部抽查单独说明。

明确缺陷由执行者修正，裁判对修正及直接受影响位置复核一次。同一问题仍未解决时保留缺陷及最短下一步，完成其余不依赖该问题的工作；不循环重写全本。仅在剩余工作确实依赖缺失来源、真实决定或额外外部权限时集中提出最小问题。

用户同时授权优化 Skill 时，将可复现的通用缺陷或明确指定的协作方式作最小修复，核验相应行为后同步源码和安装副本。项目事实、测试假设及裁判个案结论留在业务清单；已有规则足以处理的执行错误只修产物，不追加同义规程。保留首次结果与修正后结果，报告真实改进和剩余限制，不为每条反馈增加工具、测试层或新台账。

## Phase 0：完整来源和九列总账

### 1. 来源健康与控制范围

登记当前采购正文、附件、控制公告、补遗和有效澄清，说明每份是否控制本次要求。版本唯一明确时直接采用；只有缺失、冲突或无法辨别有效版时询问。备用材料损坏不影响无关来源读取。

逐文件核对哈希、页数、可打开性和真实内容。全零内容、解密失败、损坏或必要页无法读取不能当作有效来源；文件大小和名称不能代替检查。已有可靠转换成果须能回到同一原件和页码，再复用。

有可靠文本层时本地提取，并用原页检查表格、表头、勾选和跨页结构。需 OCR 时先核对 `mineru-ocr` 授权覆盖实际文件；代表页验证方法后再扩展全文。没有授权不产生上传，也不把不可读页写成无要求。

### 2. 逐范围理解

保持原始章节和编号。每次载入一个完整语义范围：条款及子项、表头连同行列与注释、一份表式及填报说明，或跨页连续内容。对每一范围依次做：

1. 看结构：自然段、表格、脚注、备注、附件、图片及跨页关系。
2. 读含义：谁在什么条件和期限内必须做什么，标准、证明、例外及不满足的后果是什么。
3. 做风险复查：否定、数量、日期、金额、条件、引用和程序后果有无漏读。风险词只帮助回查，不自动决定存在或不存在要求。

单独满足、违反、举证、评分或产生程序与履约后果的内容拆为独立要求。不得为了原子化删去解释该要求所必需的条件、例外或后果。一个段落可有多条要求，同一要求也可跨多个位置。

页面只是定位。对页内可辨识的段落、表式、注释等分别说明处理范围；整页标记只有在确实处理了全页结构后才可使用。以一个“已读”覆盖表后注释或跨页未完条款不符合验收。

来源范围采用以下结果，尚无结果就是未处理：

| 结果 | 何时使用 |
|---|---|
| `requirements_found` | 原文中已识别要求，关联对应要求编号 |
| `no_requirement` | 已实际理解，确认仅为背景、结构或不另生义务的重复内容；必要时说明理由 |
| `needs_review` | 语义、表格、版本、适用性或冲突尚未解决 |
| `unreadable` | 该范围无法可靠读取 |

被引用的附件、条款和续页必须纳入来源处置。页数和范围编号齐全只能证明登记覆盖，不证明规范内容已正确提取。

实际填写 `sources.json` 时保留脚本产生的源文件哈希、原生 `text` 及 `text_sha256`，不要在文本中改 OCR 猜测或修写原文。以 `text.splitlines()` 的 1 起算行号登记覆盖，空行也要纳入相邻范围，范围不重叠。源文件变化应重新读取并处理受影响要求，不能只改哈希消除告警。

- 顶层 `scope`：`status: "confirmed"`、本次控制范围 `basis` 和实际 `missing`。来源明确可直接按事实填写；未确认的外部公告或附件不能伪称齐全。
- 每份 `sources[]`：核对 `version`、`role`、`required`。不是当前必要采购来源时填写 `exclusion_basis` 说明用途及排除理由，不以设置非必要绕过真实缺失。
- 每页 `pages[]`：原页结构和内容可靠读取后才填 `read_status: "verified"`，在 `read_basis` 记实际核对依据。确为原页空白才可 `blank_verified: true`；扫描无文字不等于空白。
- 每页 `coverage[]`：逐块填写以下结构；`checks` 是操作者对实际完成动作的记录，不能由脚本批量添加就当作完成。

```json
{
  "start_line": 1,
  "end_line": 5,
  "status": "requirements_found",
  "checks": ["structure", "meaning", "risk"],
  "requirement_ids": ["R001"],
  "note": "本段与下一页续行合读；表后说明补充证明形式。"
}
```

`structure` 表示核对了原章、条款、表头、脚注及页内结构；`meaning` 表示逐段识别主体、义务、条件、证明及后果；`risk` 表示回查数字、否定、时限、例外及交叉引用。`no_requirement` 的编号列表为空并写理由；待核或不可读范围如实保留其状态。跨页同项要求在必要各页覆盖块均关联该要求编号，总账位置保留完整页范围。

顶层 `cross_checks.references`、`scoring`、`forms` 分别记录跨页／附件引用、实际评分规则和固定表式的源侧反查结果。`status` 仅在有据时写“通过”或“不适用”，`basis` 说明原文和处理依据；无量化评分或无固定表式允许有依据的不适用。三种视角和这三组记录仍不能由机器证明语义无漏项。

### 3. 九列要求总账

固定 UTF-8 CSV 表头，不能另加制作状态或附件页码列：

```csv
requirement_id,source_locations,source_text,requirement,type_and_consequence,satisfaction_condition,required_response_or_proof,ambiguity_or_clarification,status
```

| 列 | 写入内容 |
|---|---|
| `requirement_id` | 稳定编号；补正时尽量保留原编号 |
| `source_locations` | 必要原文的全部文件、PDF 页码和页内位置 |
| `source_text` | 完整相关原文，包含条件、例外、后果；不可只写关键词摘要 |
| `requirement` | 实际应做之事，不把内部备选策略写成采购要求 |
| `type_and_consequence` | 资格、否决、评分、格式、程序、合同等性质及不满足后果；不要自行推定废标 |
| `satisfaction_condition` | 实体标准、对象、期间、数量、金额、分值、上限等 |
| `required_response_or_proof` | 具体响应和证明形式，例如完整表式、证照有关页、签章合同关键页 |
| `ambiguity_or_clarification` | 需补充来源或人工处理的具体疑点；已处理可保留决定和依据 |
| `status` | `待复核`、`已确认`、`待澄清`、`已被补遗取代` |

这里的“已确认”仅描述要求解释；不代表证明已取得或递交已完成。适用性及依据写在要求或疑点中，实际材料与制作状态进入章节清单。

`source_locations` 单元格内每个位置独占一行：

```text
主｜采购文件.pdf｜12—13｜第二章／评分表第3行及续行
补｜采购文件.pdf｜14｜该表脚注2
修｜澄清文件.pdf｜1｜第2项
冲突｜附件说明.pdf｜3｜说明第4段
```

只有实际存在相应关系才用 `主／补／修／冲突`。连续跨页保持一个完整范围；PDF 物理页与印刷页不一致时说清两者。CSV 由标准库或表格工具写入，含换行和逗号的单元格须正确引用。

补遗改变同项要求时保留原位置和修改位置，正文表达当前有效要求，保留先前冻结版本；不能把仍然有效的现行行误标成“已被补遗取代”。确实整体撤销或另项替换时才用取代状态。无法协调的有效来源进入待澄清，不由模型自选。

脚本中将旧条目标为“已被补遗取代”时，在疑点栏写 `替代要求：Rxxx`，指向总账中存在且已确认的现行条目，旧条目的来源仍须核对。整项取消也可直接在原稳定 ID 的现行行写明“根据补遗不再要求……”并保留取消原文和 `修` 位置；不能用“撤销依据”几个字绕过核对。引文的多段原文用换行、`---`、换行分隔，脚本会去除空白后与所引页文字比对；原页与文本层差异需回读解决，不能随意改写引文。

### 4. G1/G2 与人工冻结

先从全部来源反查候选，再由候选回读必要原文。额外注意普通段落、合同、表后说明、勾选适用性及跨章引用。评分文件应核对实际采用的公式、分值、上限、权重和计数单位；没有量化规则时不强凑总分。

| 检查 | 可进入冻结的条件 | 保持工作版的事项 |
|---|---|---|
| G1 来源与版本 | 当前控制来源明确且可读取，必要附件已纳入 | 缺必要来源、版本未定、关键来源损坏或不可读 |
| G2 要求完整 | 所有范围已处置、要求可回读、影响含义的疑点已解决 | 未处置或待核范围、未解冲突、跨页或评分条件不完整 |

冻结前给用户可核阅的总账和一页说明：采用来源与版本、阅读范围、要求及高风险项、已处理实质疑点、剩余限制。请求一次明确冻结决定，并将决定绑定该来源和要求版本。不能替用户点击确认或把无回答当确认。未达到 G1/G2 时保存工作版；用户可决定继续编制，但不把工作版登记成通过真实阶段验收。

仅在取得对应真实决定后执行：

```bash
python3 "<skill-root>/scripts/tender.py" freeze --project "<项目内部工作目录>" --reviewer "<实际复核人>" --decision-reference "<本次人工确认依据>" --expected-digest "<已展示并获确认版本的digest>"
```

冻结保存该版本来源与总账副本；输入改变后 `freeze_status` 为 `stale`，不得照用旧确认。冻结命令验证记录和版本，不能自行证明传入的复核人或确认依据真实存在。

### 5. 回放质量

首次提取上下文只提供采购来源，先保存原始候选再看历史响应或人工补正。记录候选正确提取、漏提、错误解释和重复，人工补正后的结果单列。已经看过的项目称“已知样本回放”。

以完整原件作参考，人工复核后的全部必需项、评分规则及程序条件应可追溯；高风险要求原始候选零漏提是样本工具验收目标。出现漏提就修正方法，最多一次纠正复查；仍漏提则不声称可进入下一真实阶段。测出脚注新增要求、跨页条件缺失或无效附件，说明的只是所测情形。

## Phase 1：章节映射、生成和局部变更

### 1. 一份分层清单

清单顶部保存控制来源及总账版本，以及本项目已确认的主体、团队、服务期、报价轮次和关键承诺，连同各值的来源或决定。未知值保持待定。下层先列真实对外交付物与目录，再按可独立完成的表式、人员、业绩类别或方案主题分单元。

每个单元只需说明：相关要求；采用材料和页码或批准值；应交什么；实际输出和位置；未决项与完成状态。具体机器字段由脚本生成的 JSON 及帮助约定，不能平行维护另一份要求表。

填写和运行两章工具时另读 [chapters.md](chapters.md)。`chapters.py` 负责抽取必要上下文、字面模板替换、依赖影响和确定性计分；它不是自行起草技术方案的模型。Codex 根据实际包中原文完成需要语义理解的写作，再回填结果与缺口。

映射时注意：

- 同一要求需要正文、附件和独立文件三处响应时，三处均有落点。
- 保证金、原件备查、现场述标、密封等进入执行事项，不强凑正文。
- 匿名、禁止报价等全局规则注明适用卷册并交给相关单元完整原文。
- 每项现行要求有响应、待补件、待判断、待执行或有依据的不适用处置。

要求编号已挂接、存在同名章节或写有总括接受，不证明具体响应齐全。对实际条款核对对象、数量／频次、限制和例外，对表格核对每个必填栏所问的事实；不能用其他栏的答案或相关词句充数。以“未经同意”“违法”等条件放宽采购文件的绝对禁止，应按原文修正；来源不明的具体事实保留待核，不由裁判补造。

### 2. 证明和计分

先核对对象、本人参与、时间、业务范围和具体证明形式，再采用材料。文件名或相似项目名称仅用于查找。同一来源未变可复用核对和选页；换一项评分标准需重判其符合范围。要求完整文件时不得擅自只选关键页。

本小节没有出现某份证明，不等于整册缺失。先沿目录及明确引用定位其他章节，核对实际内容后在同一清单记录复用位置。只能核到部分范围时写“已核范围未见，其他位置待核”，不能写“全项目缺失”。执业年限等数据按采购规定的起算依据和同一时点重算；证号年份、年度备案页、社保期间及打印日期分别记录，历史表格的年限不能直接当作当前值。

按采购文件的公司／独立项目／个人单位计数，副本不计新增数量。量化计算采用确认输入和公式；缺竞争对手报价不输出所谓真实价格得分。主观项只说明响应内容和风险，预估分与评委得分分开。

默认满分最低数量外再准备一份合格业绩，不超分值上限、不用弱相关材料凑数。页数、数量、匿名、保密、新增承诺或显著工作量冲突时集中交人决定。有价值的可选响应同样按此原则准备。

缺件条目说明“缺什么、可接受形式、找谁、何时需要、影响什么”。同一材料解决多项缺口时合并索取；形成清单或草稿不等于已获准外发消息。

### 3. 有限上下文和章节产物

每次提供本单元任务、相关要求全文及全部必要位置、适用全局约束、材料关键页、批准事实、格式来源和上一接受版本的修改范围。不要把全采购 Markdown、全部人员档案、历史标书或其他章节全文交给所有单元。

短单元可同上下文顺序处理；长且材料独立的单元使用不继承全部聊天历史的上下文。验证时记录实际传入内容，不能仅凭一个“章节包”文件声称已隔离。每个单元只有一个写入者，避免并行改同一主文档。

产物含实际章节工作稿及必要证明、已响应要求、缺口和采用版本。人员表与服务安排使用同一批准团队和承诺。技术方案必须回应采购需求及相关合同义务，写清工作、责任人、时间和结果，不能只照评分表堆机构介绍。

执行 G3/G4：从要求看回应是否齐全，从章节看事实、承诺与证据是否有依据；核对声称“已附”的材料实际存在。当前授权书、承诺函待签章可先生成；证明既往事实的合同缺必要签章仍保留缺口。

### 4. 一次可回放的局部变更

用明确标识的模拟人员替换，或已获决定的真实变更，查询清单实际引用：团队表、本人证明、个人业绩、分工、承诺、PPT 等。更新受影响内容及分页、目录、抽页；记录变更依据、影响范围及结果。无关章节不重写。

来源、事实或文件改变后，旧文件绑定的检查过期。仅分页变化可保留未变内容的事实核对，但重做最终位置检查；已经打印或流转用印的旧稿需提示停止使用并确认替换，本地修改不表示外部已收回。

先保存内容补正后的基线，再回放单一业务值变化，分别记录“原稿到补正基线”与“基线到变更稿”的差异。岗位分工调整不当然改变人员资格或计分，人员变更也不能只改姓名而保留旧证明；按实际依赖核对正文、证明、计分和下游文件。

实测两章可恢复、共享值一致、变更范围正确后才记该阶段结果。尚未冻结真实总账时，已获授权的内部历史回放可使用明确测试假设继续，原疑点、证据缺口与执行状态照实保留；只能报告所测范围，不能冒充真实 Phase 1 验收。

## Phase 2：文件装配与真实执行

实际运行装配、抽页和状态命令时读 [assembly.md](assembly.md)，其中说明已实现的参数、清单字段与版本绑定。

### 1. 文件集与格式

只制作本项目需要的主文件、独立文件及执行派生。在同一章节清单列出每个准确文件、用途、编辑来源／批准数据、版本、适用要求与执行事项。装订和独立递交两种用途均有要求时，两份都准备。

采购目录、固定表式、编号、卷册及字段优先。仅部分规定时填充未规定部分；完全未规定时按适用内容安排简洁目录，不强制固定四章。已获准的历史参考只控制未被当前采购文件规定的结构和版式，不提供当前事实、价格或承诺。

DOCX、PPT 使用当前环境已有文档能力；PDF 脚本用于已验收页面的合并、抽取和映射，不自行保证版式正确。正式文书生成后在实际文件上核对表式、必填项、目录、附件和内容可读性。采购文件允许的合法留白、完全接受时可空的偏离栏和待签章位置，按依据判断，不一律报错。

独立报价使用同一已批准轮次、币种、税费、服务期和金额。采购次数与报价轮次分别判断；“第二次采购”不推出“第二轮报价”。同轮金额冲突需处理，不同轮次有明确来源且采用关系清楚时允许不同金额。

### 2. 页映射和派生

从准确总稿按既定顺序装配，页映射能回答每个输出页来自哪份源文件的哪页。建立常规／用印分拆时核对两部分完整覆盖预定总稿范围，以及必要重复页。独立抽页应保留用途和来源范围，不凭文件名推断完整。

每次检查绑定准确源文件和输出哈希。总稿修改后重新产生相关抽页、目录和页引用，不能手工在派生文件另改业务内容。输出可打开、页数正确不等于证明可读，仍要看实际页。

签章回传先保留收到的文件，再核对与待签章版的文字、页序、应签位置及新旧差异；哈希变化本来就可能发生，不要求相同。只增加获准签章时核对执行及内容未被改动；无法解释的差异保持待核。可观察的签章不代表能够鉴定真伪或权限。

### 3. 分阶段检查和人工处理

每项检查记录对象、结果、证据位置及必要补正；结果为通过、阻断、待核、不适用，不适用须有项目依据。检查与人作出的处理决定分开留存：

| 检查 | 当前阶段的关键风险 |
|---|---|
| G1 | 控制来源、版本、材料健康及读取范围 |
| G2 | 从原文反查要求完整，跨页、脚注、勾选及附件引用 |
| G3 | 每项必需回应和证明实际出现，证明对象、时间及形式正确 |
| G4 | 主体、人员、期限、承诺、同轮报价、独立计分及上限一致 |
| G5 | 目录、页序、表式、附件、独立文件、必填字段及版式可读 |
| G6 | 拟用文件与受检文件一致，旧件已处置，当前阶段执行事项有依据 |

正文及待签章稿可提前编制。强制缺口不隐藏；用户决定采用替代材料或带缺口继续时，说明原要求、采用方式、影响及决定人，按授权推进，保留“未取得”“尚未获采购人认可”等真实状态。相同决定不重复阻拦。评分不足单列有依据预估、争议及损失，不能改为满分。

常规状态顺序为：

```text
工作稿 → 待签章／待执行候选 → 人工批准递交 → 已递交
```

工作稿允许明确缺口。待签章说明内容候选与待办签章，不能声称已完成执行；人工批准递交必须有对应明确决定，并展示残余缺口和检查结果；已递交须有对应凭据或有依据的人员确认。采购人接受、中标另有证据，不由已递交推定。采购要求电子签章时按实际方式核对。

递交回执是事后依据，不成为递交前生成工作的前置条件。未经明确授权不外发材料、执行签章、上传或最终递交。

### 4. 阶段结论

给人一页可决策结果：准备的是哪组准确文件、拟进行何种执行、强制缺口及评分风险、未批准承诺、待签章和待递交事项、需替换旧件。报告前重读本轮文件集的实际哈希并写回现有清单；保存或导出又改变文件时，先核对变化再沿用受检结论。合成文件、已知样本回放、实际签章、递交和接受分别说明。

保留有复核用途的源映射、冻结总账、采用证明、当前编辑稿及真实回执。内部文字提取、渲染和缓存集中到内部过程目录；本轮确认不再复用的临时文件可恢复清理。
